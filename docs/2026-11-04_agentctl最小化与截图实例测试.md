## 3. 10:24 原始故障的状态

```text
ctl_windows: ZCode rect [494,207,2067,1332]，minimized=false，cloaked=false
ctl_focus  : foreground=false（code 5/10）
ctl_shot   : 返回成功，但图是渐变灰底
```

这个状态**没有**在测试矩阵 3–5 中复现：

- 真正最小化时，`ctl_windows` 会报 `minimized=true`，`ctl_shot` 会拒绝，`ctl_focus` 能恢复；
- 普通遮挡时，`ctl_shot` 能正常取到内容。

因此 10:24 的灰底不是“最小化”本身，也不是“遮挡”本身，而是 **窗口存在但没有已绘制的合成表面（未 paint / 瞬态 compositor 状态）**。也可能是当时窗口刚启动、一直没到前台，Chromium 尚未完成首帧。

## 4. 确认的组件缺陷

1. **灰底被当成成功**：`ctl_shot` 对“渐变灰、无文字、无控件”的图没有识别为空白，仍返回 `ok=true`。现有 `_looks_blank` 只看灰度 stddev <3，渐变灰能绕过。
2. **`ctl_focus` 失败原因不明确**：当时只返回 `foreground=false`，没有区分“最小化 / 另一虚拟桌面 / 未响应 / 前台锁”。
3. **状态快照与动作时不一致**：`ctl_windows` 的 `minimized`、rect 是快照值；动作前需要重新 `IsIconic` / `GetWindowRect`，不能复用旧快照。
4. **未暴露虚拟桌面状态**：`ctl_windows` 没有 `on_current_desktop`；如果窗口在另一虚拟桌面，表现会和“未 paint”很像。

## 5. 修复（已实施）

### 5.1 `perceive.py`（截图）

- `_looks_blank` 从“只看 stddev<3”改为四项联合判据：
  - 全图 stddev；
  - 灰度范围；
  - 边缘密度；
  - 3×3 分块的最大边缘/最大 stddev。
- 新增 `_client_crop()`：空白判定只看客户区，避免窗口边框/黑边把灰底“救活”。
- `shot()`：PrintWindow 连续重试 3 次；仍空白则返回
  `{"拒绝": "...", "空白": true, "重试": 3, "指标": {...}}`，不再把灰图当成功。
- 保留原来的最小化拒绝、前台屏幕抓取退路。

### 5.2 `act.py`（置前）

- `do_focus()` 改为调用 `_try_foreground()`，失败时做一次
  `AttachThreadInput + BringWindowToTop` 最后尝试（仅显式 B 级 ctl_focus 使用）。
- 失败时区分并返回具体原因：
  - `IsIconic` 仍为真 → “窗口仍最小化（SW_RESTORE 未生效）”；
  - `DWMWA_CLOAKED=1` → “窗口被 DWM 隐藏（可能在另一虚拟桌面）”；
  - 前台仍是别的窗口 → “前台锁/另一桌面”。
- 新增 `_window_state_bits()` / `_hard_foreground()`。

## 7. 结论

- 不是 ZCode 客户端坏了。
- 不是“最小化窗口必然灰底”；恢复逻辑本身可用。
- 确认是 **agentctl 截图/置前组件对“未绘制表面/瞬态状态”缺少识别与分类**，把灰底当成功，且 focus 失败没给出可操作原因。
- 已修 `ctl_shot` 的空白检测/重试/拒绝，以及 `ctl_focus` 的恢复与状态分类；`ctl_windows` 的最小化字段在本次实例测试中表现正确，暂不改。
- 当前会话的旧 MCP 进程需重启才能加载新模块；新进程已用纯灰窗口验证通过。
